# DV20 - Plan Journal

Append-only log of the 5-agent role-less architecture audit loop for the forward-swipe Messages → `/search` feature. Each round: 5 independent auditors examine `docs/DV20-Plan.md` against the live codebase under an open-ended, architecture-level standard; loop until 5/5 unconditional PASS. Full detail per round in `DV20-Audit-R{N}.md`.

The plan arrived in this tree in an **R1-revised state** (a prior, unrecorded pass found 0/5 PASS on the original cross-component handoff design and identified three blockers: the `clientX` source, the GPL visualDragOffset sign-asymmetry, and the goto timing race; the plan was revised to add the raw `pointermove` listener, the forward `visualDragOffset` branch, `detectSwipe.claim`, and the `pointerReleased` fallback). Round 2 below is the first recorded round; it audits the R1-revised plan.

## Round 1 (prior, unrecorded in this tree; 0/5 PASS → revised)

A prior pass found the original cross-component handoff design 0/5 PASS on three blockers: (B1) MobileTabPager's swipe handlers receive only `deltaX`, not absolute `clientX`; (B2) the GPL `visualDragOffset` was believed sign-asymmetric (back-swipe only); (B3) `goto` is async and the pointer may release before the GPL mounts. The plan was revised to its current R1 state (raw `pointermove` listener for `clientX`; forward `visualDragOffset` branch + `detectSwipe.claim`; `pointerReleased` fallback to `enterRaf`). No `DV20-Audit-R1.md` artifact exists; this summary is reconstructed from the plan's Status line.

## Round 2 (0/5 PASS, 5/5 FAIL, unanimous → revised)

Five independent auditors examined the R1-revised plan against the live codebase. All five FAIL, all high confidence, all organic = has-special-cases. Full detail: `DV20-Audit-R2.md`.

Convergent blockers:

- **R2-B1 (5/5):** the forward `visualDragOffset` geometry is wrong by one full panel width. The live `trackTranslateX` base when `visualDragOffset !== null` is `-ACTIVE*STEP_PERCENT%` (the `/search` rest position), not `snapIndex=0` (Messages). At `dragOffset=0` the track is at `-50%` (`/search` visible, not Messages); at `dragOffset=-W` the track is at `-2W` (blank). The plan never modifies the base, so §2.3 B2's stated behaviour is arithmetically false.
- **R2-B2 (5/5):** `detectSwipe.claim` does not seed `maxX`/`minX`/`samples`, so `finish()` reads `rebound = event.clientX - 0 ≫ 25`, classifying every release as `reversed`; the forward swipe never commits.
- **R2-B3 (4/5):** visual discontinuity at the swap (MobileTabPager's 0.4x rubber-band rest at `-2W` vs the GPL's `/search` rest at `-W`); a one-frame teleport of roughly half the viewport.
- **R2-B4 (4/5):** `enterRaf` (`:932-937`) fires unconditionally on mount and races the handoff drag; the cancel path snaps to `/search` before `history.back()`.
- **R2-B5 (3/5):** `onSwipeEnd` has no forward-commit branch (`committedRight` is always false on `/search`); the plan's §2.6 commit/cancel semantics are unimplementable, and §3 does not list modifying `onSwipeEnd`.
- **R2-B6 (2/5):** the plan's `swipeMove` guard uses `reversed`, which `MoveHandler = (deltaX) => void` cannot deliver.
- **R2-B7 (2/5):** pointer events are lost during the DOM swap (MobileTabPager `destroy()` releases capture and removes listeners before the GPL mounts + claims); a `pointerup` in the gap strands the gesture.
- **R2-B8 (5/5, architecture gate):** 7-to-9-piece parallel gesture pipeline (handoff store + raw pointermove listener + `claim` + `swipeDirection='forward'` literal + forward `visualDragOffset` branch + `onSwipeMove` guard relaxation + `pointerReleased` fallback + `onSwipeEnd` forward branch + root-layout safety net), violating `architecture-consistency-single-transition-mechanism` and `two-mechanism-unification-not-bridge`.
- **R2-B9:** the R1 premise ("visualDragOffset is sign-asymmetric") is false; the existing else branch (`:453`) already mirrors the back-swipe. R1 solved a non-defect and missed R2-B1.

Unanimous recommendation: **drop the cross-route handoff.** On the commit threshold MobileTabPager calls `goto('/search')`; `/search`'s GPL mounts with `shouldAnimateEnter = true` and the existing `enterRaf` plays the 200 ms CSS slide-in. New code: one forward-commit branch in `swipeEnd` + the `forwardDeepNeighbour` data field. Zero new stores, overlays, resolvers, handoffs, `claim`, or `trackTranslateX` changes. This matches the owner's "least fragmentation" directive.

Open product question (the audit cannot resolve): whether the 1:1 forward-drag preview is a hard requirement. If yes, the only clean 1:1 option is to host `/search` as a real fourth tab under the MobileTabPager (both directions become intra-pager tab swipes; one mechanism; fully symmetric), which changes the product's navigation structure (the tab bar gains a Search entry). Round 3 audits the chosen direction.

## Scope pivot (post-R2, 2026-07-04)

The R2 unanimous FAIL, plus the owner's architectural critique, reframes DV20's scope. The forward-swipe-to-`/search` difficulty is a symptom of a deeper fragmentation: the navigation/gesture layer has no underlying state machine as a single source of truth, so state is smeared across roughly 20 flag variables in 4+ stores/components (GPL's `dragOffset`/`swipeDirection`/`snapIndex`/`isPendingNavigation`/`isTransitioningOut`/`pendingCancel`/`swipeNeedsLoadingAtStart`; MobileTabPager's `activeIndex`/`dragOffset`/`showDeepPreview`/`backChipReveal`; navStore's `pendingNav`/`navInFlight`/`direction`; pager store's `fractionalIndex`/`dragging`/`backMorph`/`coverProgress`/`tapMorph`; plus implicit CSS-transition state read back via `transitionend` and computed-style polling). Around 130 imperative route-classification call sites (`hopForHref` 30, `getCurrentTabIndex` 27, `backSwipeShouldPopHistory` 22, `isOverlayRoute` 19, `isTabRootPath` 15, `isComposeRoute` 8, `isPagerRoute` 6, `isGesturePageLayoutRoute` 3) encode the same shallow-vs-deep question everywhere. MobileTabPager's track is hardcoded to three panels (`w-[300%]`, `w-1/3`, `section0/1/2El`), not data-driven.

The owner's target architecture is a two-layer state machine:

1. **Page-depth classification** as a data property of each route (shallow / deep / special; where `/search` falls is an open research question).
2. **A navigation/gesture state machine** whose state is (current page, current depth, gesture intent, animation phase); the gesture target is read directly from the route stack plus page depth (no special-casing); the state machine publishes the current phase during animation as the single source of truth that the animation mechanism and all consumers (FAB, Header, scroll-chrome) read.

Plus a unified cache (replacing list-cache + deep-page-snapshot + page-scroll), a single animation mechanism (replacing the CSS-transition + JS-RAF split), and a uniform page lifecycle (mount/activate/deactivate/unmount across depths).

A neighbor-graph unification (my earlier proposal) was rejected: it is still the spatial-track model in data-driven form and does not introduce a state machine.

DV20 is re-scoped from a forward-swipe point-fix to this state-machine redesign. The forward-swipe to `/search` becomes a natural consequence of the redesign, not a special case. Round 3 (the audit of the revised plan) is deferred until a research investigation grounds the redesign. The research runs in five parallel lines: (1) page-depth taxonomy and `/search` classification; (2) reverse-engineering the current implicit state machine; (3) cache fragmentation inventory; (4) animation-mechanism fragmentation; (5) page-lifecycle fragmentation. The synthesis becomes the new DV20-Plan draft, which then enters the 5-agent audit loop.

## Research synthesis (2026-07-04)

Five parallel read-only research lines completed. Findings converge on the owner's two-layer state-machine vision and fill the per-layer detail.

**Convergence.**

- (1) Page-depth taxonomy: shallow/deep is a derived property (membership in the spatial tab layout), not a structural axis; `/search` is deep with orthogonal attributes `headerMode=search` and `subPager=search-scope`; the discussions/detail and messages/detail pairs express their relationship via a `backParent` data edge (centerTab derives from it); Activity has no detail because no deep route declares it as backParent. Around 138 route-classification call sites collapse to one DATA record per route. Latent bug found: `isGesturePageLayoutRoute('/search')` returns false today despite `/search` mounting a GPL.
- (2) Implicit state machine: 22 implicit phases across roughly 20 state variables in 4+ stores/components. Sharpest contradictions: the 4 hand-written `committed` predicate copies; the GPL-vs-MTP commit-mechanism asymmetry (GPL uses `pendingNav` + `transitionend` + rAF poll with an 800 ms cap; MTP calls `navigateBackward` directly + `setTimeout(300)`, no `pendingNav`, no transitionend consumer); the dual read-back of `trackEl.transform.m41` by two rAF samplers plus `transitionend` as a third parallel signal; the stealth `navInFlight = false` writer in `GPL.onSwipeMove`; `pager.dragging` overloaded in MTP to include `backChipReveal`; `backMorph`/`coverProgress`/`tapMorph` published GPL-only; three "where are we going" strings (`resolvedLeftHref`, `lockedLeftHref`, `pendingTargetHref`); an uncancellable `preloadData` promise racing the cross-tab tap chain.
- (3) Cache fragmentation: 4 singletons (`list-cache`, `deep-page-snapshot`, `page-scroll`, `search-cache`) plus 2 SvelteKit `snapshot` exports; all differ on key shape, value shape, invalidation, and reader contract; 10 documented bugs. Unified `PageCacheStore`: key `(pathname, subKey)`, value `{data, discriminator, snippet?, scrollTop, source, capturedAt}`, single `capture`/`get`/`invalidate`.
- (4) Animation mechanism: 16 CSS transitions + 8 rAF loops + 2 `transitionend` handlers + 2 computed-style polls; 9 double-animation conflicts (CSS + rAF writing the same property); 8 overlapping gates (`transitionEnabled`, `discreteNavInFlight`, `pendingCancel`, `slideT`, `pager.dragging`, `pager.tapMorph !== null`, `navStore.navInFlight`, `chipExitActive`). Unified by `GesturePhase` as the sole discriminator with the invariant: exactly one of {CSS transition, rAF write, inline static value} owns each property's motion, decided solely by `phase.kind`.
- (5) Page lifecycle: 5 mounting regimes (tab root in MTP; thread; conversation; `/search`; generic deep; compose), 4 lifecycle-adjacent stores (`viewport-lock`, `scroll-chrome`, `active-gesture-track`, `page-scroll`), 7 asymmetries with documented reasons. Unified 4-phase contract: `mount` / `activate` / `deactivate` / `unmount`, owned by the layout that mounts the gesture surface, with the adjacent stores refactored as lifecycle hooks.

**Validated architecture: five-layer unidirectional pipeline.** Layer 1 lifecycle orchestrator (macro phases: `at-rest`, `intent`, `resolving`, `transitioning`, `landing`) owns the navigation lifecycle, interruption handling, and SvelteKit interop (`beforeNavigate` cancel + preload + redispatch, not bypass). Layer 2 intent classifier maps raw input (pointer events, taps, popstate) to intent + continuous params. Layer 3 resolver: pure function `(intent, stack, spatial layout, route DATA) -> (strategy = GesturePhase kind, FROM, TO)`, resolved once per gesture. Layer 4 coordinator: consult the unified `PageCacheStore`; hit -> direct slide; miss -> chip-exit + preload. Layer 5 executor: the unified animation mechanism; the only layer that touches the DOM. The orchestrator and the intent layer are the macro and micro of one transition, not two independent machines.

**Route DATA model (one record per route, replaces ~138 classifier call sites).** `depth` (derived: is in spatial layout); `gestureOwner` (`mtp`/`gpl`/`none`); `headerMode` (`root`/`deep`/`search`); `fabFamily` + `fabKind`; `tabModule` (`discussions`/`activity`/`messages`/`inherit`/`none`); `backParent` (replaces `getParent`; detail pages declare their source tab, centerTab derives); `subPager` (`none`/`search-scope`); `snapshotCapture` (boolean).

**State machine phases (the 22 implicit collapse to this explicit set).** Macro: `at-rest-on-tab`, `at-rest-on-deep`, `dragging`, `committing` (`commit-slide` / `chip-exit`), `cancelling`, `animating-enter`, `scrubbing`, `landing`. Micro (intent layer): `idle`, `deciding`, `drag-left`, `drag-right`, `committed`, `cancelled`. The phase record carries `(from, to, startTime, duration, easing, liveOffset)` and is the sole input to every consumer.

**Structural defects eliminated.** 4 `committed` predicate copies -> one `phase === 'committed'`. GPL/MTP dual commit implementation -> one (state-machine-driven; MTP no longer calls `navigateBackward` directly). Dual `trackEl.transform.m41` read-back -> authoritative state. 8 overlapping gates -> one `phase.kind`. 4 cache singletons -> one `PageCacheStore`. MTP hardcoded 3 panels -> data-driven. ~138 route-classification calls -> DATA records. The 9 double-animation conflicts -> structurally impossible under the one-clock-per-phase invariant.

**Open decisions for the owner.** (1) Scope and phasing: independent architecture DV (DV20 re-scoped or DV21), phased over four stages each independently audited with e2e (DATA model first; then unified cache; then state machine + phases; then animation mechanism), or one-shot rewrite. (2) The original forward-swipe-to-`/search` requirement: in the unified architecture it is a FROM-shallow/TO-deep resolution, defaulting to commit-then-enter (no 1:1 drag preview); accept the default, or require 1:1 (which requires promoting `/search` into the spatial layout, i.e. a product change). Two minor defaults applied unless overridden: SvelteKit `snapshot` retained (orthogonal to the unified cache); `headerMode` kept three-valued with the enum reserved for extension.

On owner confirmation of the architecture and the open decisions, the full DV20-Plan draft is written (per-layer file-level changes, migration phasing, test plan, e2e strategy), then enters the 5-agent audit loop.

## Macro architecture document + Cycle model (2026-07-04)

The owner refined the design across the discussion and authorized converting DV20 into a macro architecture document. The refinements, captured in `docs/DV20-Plan.md`:

- **Tags replace the depth axis.** Pages carry tags (`tab`, `detail`, `search`) that name the transition family they participate in, not a hierarchy level. The orchestrator selects a resolver by the (from-tag, to-tag) pair; six pairs for three tags; each pair has one symmetric resolver parameterized by progress direction (0 to 1 enter, 1 to 0 exit). This is the open-closed generalization of the shallow/deep binary (the binary is a degenerate two-tag system); it eliminates the hardcoded binary branching.
- **The resolver lives inside the state machine and is a pure function** of (intent, stack, from-tag, to-tag, direction), outputting a per-consumer animation plan (page-track direction and distance, FAB scale/translateY, Header morph/title-crossfade) as functions of (progress, liveOffset). The resolver never touches the DOM; consumers execute the plans.
- **All-rAF executor; CSS transitions removed entirely.** The owner's directive: pure CSS animation must be eliminated, everything managed by one rAF loop, otherwise logic fragments further. The structural invariant: exactly one rAF write owns each visual property's motion, decided solely by the orchestrator's phase. This enables the long-missing velocity-matched commit: the release animation takes the finger's release velocity and integrates the remaining distance with a critically-damped momentum integral, replacing the hardcoded 200ms ease that made the gesture feel inconsistent.
- **`{tab, tab}` handles both spatial swipes and tab-internal pagination atomically.** The `{detail, detail}` resolver owns the Header title push/squish crossfade, moving the Header's internal settle machine into the resolver.
- **Eight refinements to handle in the Cycle specs** (not blockers): prefers-reduced-motion in the executor; commit interruption by a re-grab; velocity-matched edge cases (near-zero fallback, high-velocity clamp, integrator); detail-to-detail Header title readiness under async load; `{tab, tab}` pagination; SSR safety; the SvelteKit-orchestrator ownership boundary; SearchScopePager nested composition.

**Execution model.** The architect owns the macro architecture and each Cycle spec. A Cycle Manager Agent (CMA) implements each Cycle and runs its audit (five independent role-less auditors to 5/5 unconditional). The CMA is instructed on documentation (Cycle journal + audit-round files, revision history in the Cycle Plan-Journal), on multi-agent invocation (open-ended, no leading prompts, no count cutting), and on anti-cheating (paste real gate outputs; no PASS without evidence; no preventive test means no fix; no CSS-transition/setTimeout/parallel-mechanism/hardcoded-200ms shortcuts; deviations flagged to the architect, not decided unilaterally). The architect reads each Cycle's report, verifies against the spec and the §13 values, and decides rework or advance.

**Cycle slicing.** Cycle 1 route DATA model + tag taxonomy (low risk, foundation). Cycle 2 unified `PageCacheStore` (medium, independent). Cycle 3 state-machine core + tag-pair resolvers, Layers 1 to 4 (high risk, the core; depends on 1). Cycle 4 all-rAF executor + velocity-matched commit, Layer 5 (high risk; depends on 3). Cycle 5 `PageLifecycle` contract + route-by-route migration with full e2e (cross-cutting, final; depends on 1 to 4). Cycle 2 may parallel Cycle 3 once Cycle 1 lands.

**Open decisions pending owner sign-off** (`docs/DV20-Plan.md` §14): (1) three independent tags vs `search` as `detail` plus a `headerMode` attribute (architect recommends three); (2) the non-adjacent-tab back-swipe visual under generic stack-based back (architect recommends the generic version); (3) the Cycle sequencing and parallelism. On sign-off, Cycle 1 is spec'd in detail and its CMA is launched.

## Sign-off, anti-cheating correction, Cycle 1 launch (2026-07-04)

Owner signed off and gave the green light to start work. Three corrections to the protocol, applied to `docs/DV20-Plan.md` §11 and §14:

1. **Prescribing checks is itself cheating.** The §11 anti-cheating list previously named the exact gates (`bun run check`, `bun run lint`, `bun test`, `bun run test:e2e`). The owner's correction: telling the CMA what to verify lets it follow a recipe rather than demonstrate it knows what correctness means. §11 now states the CMA decides what to verify and how; the architect does not prescribe a checklist; a claim without real evidence is a failure.
2. **PASS with concerns is not PASS.** §11 now states the bar is 5/5 unconditional PASS with zero concerns; any concern from any auditor blocks completion.
3. **Audits must be role-less and hint-less.** §11 now forbids role assignment, named or suggested defects, suggested verdicts, references to "the fix", and any implication of what to look for. The audit prompt is an open instruction to find any defect empirically. (This has failed before.)

Signed-off decisions (§14): (1) three independent tags; (2) the slide direction is the resolver's job, spatial for `{tab, tab}` and intent-plus-stack for cross-tag pairs, so the non-adjacent-tab case is not a separate product decision; (3) Cycles sequenced by default, parallel only for provably file-disjoint pairs (the agents are unaware of each other).

Cycle 1 spec written: `docs/DV20-Meeting/DV20-Cycle-1-spec.md` (route DATA model + tag taxonomy; behavior-preserving; the record is the single source of truth; fixes the latent `isGesturePageLayoutRoute('/search') === false` bug structurally). CMA1 launched in the background. The architect reviews CMA1's report against the spec on completion and decides rework or advance.
